The Problem · Chapter 2

Auto-Sync vs Progressive Sync

Auto-Sync

Progressive Sync

Environments sync one at a time, in order.

Auto-sync reacts to the same commit in every environment at once: nothing orders the syncs. Progressive sync marks everything out of sync, then syncs one environment at a time.

The Problem · Chapter 3

First Prod Outage: The New Version Is Bad

Readiness gates are passing, but the application is failing. Even with multiple environments, the new code can still break production.

HealthyOutage  Deployment Rolls Out to 100% of Pods

Blast radius: 100% of pods, no rollback.

Passing dev and staging doesn't guarantee prod is fine: different traffic, data, scale.
The Problem · Chapter 3 · The Fix

Progressive Delivery With Argo Rollouts

Canary at the workload level: shift traffic gradually, analyze metrics, auto-abort on failure.

Fix  Canary 10% → 50% → 100%

Analysis fails at the first step, so the rollout is aborted.

Blast radius: 10% of pods, then rollback.

Adopt progressive delivery at the workload level: Argo Rollouts, canary / blue-green + analysis.

How It Works

Wait, Disable Auto-Sync?!

We thought that was bad practice.

It's OK. The progressive sync strategy replaces auto-sync. Both are automated processes; only one of them may drive syncs.
  • Applications generated by ApplicationSet using Rolling Sync strategy have auto sync disabled
  • The ApplicationSet controller decides when each Application syncs
  • Feature is opt-in on the controller (Beta)

Generated Application

kind: Application
spec:
  syncPolicy:
    # no "automated" block
    # = auto-sync disabled
    retry:
      limit: 2
Verify the exact flag/config key before presenting (applicationsetcontroller.enable.progressive.syncs in argocd-cmd-params-cm). Also confirm how the controller treats a template that sets syncPolicy.automated.
How It Works

Opting In: Two Separate Switches

Step 1

Enable It on the Controller

Or pass --enable-progressive-syncs, or set ARGOCD_APPLICATIONSET_CONTROLLER_ENABLE_PROGRESSIVE_SYNCS=true.

# argocd-cmd-params-cm
data:
  applicationsetcontroller.enable.progressive.syncs: "true"
Step 2

Set the Strategy in the ApplicationSet

Define the steps under rollingSync (next slide).

kind: ApplicationSet
spec:
  strategy:
    type: RollingSync

Docs: argo-cd.readthedocs.io/en/stable/operator-manual/applicationset/Progressive-Syncs

Two separate switches: one global on the ApplicationSet controller, one per ApplicationSet. Source: Argo CD docs, Progressive Syncs. Replace the YAML visuals with real screenshots if you prefer.
Grouping Apps

Steps Select Applications by Label

kind: ApplicationSet
spec:
  strategy:
    type: RollingSync
    rollingSync:
      steps:
        - matchExpressions:
            - {key: wave, operator: In, values: [dev]}
        - matchExpressions:
            - {key: wave, operator: In, values: [staging]}
          maxUpdate: 1
        - matchExpressions:
            - {key: wave, operator: In, values: [prod]}
          maxUpdate: 25%
  template:
    metadata:
      labels:
        wave: '{{.wave}}'
  • Label each generated App with its wave
  • Steps run in order
  • maxUpdate caps apps syncing at once inside a step (number or %)
  • Next step starts when the previous one is Healthy
Verify YAML against current docs (operator, maxUpdate semantics, goTemplate form) before presenting.

Complexity

How Do You Detect “A Change”?

Is a change a new Git revision? Nooo. It's more complicated.

  • A new commit may not change this Application's rendered manifests
  • A change can be a spec edit on the Application itself (source, values, target revision…)
  • Several generators/sources can contribute to one Application
  • A refresh is triggered as soon as we detect an Application may have a new revision
  • The controller must tell "needs a rollout" from "just refresh"
Fill in the real detection logic (OutOfSync + comparison of sync revision / app spec) once confirmed against the controller code.

Limitations

What to Know Before Adopting

Coupled to ApplicationSet

Apps not generated by an ApplicationSet can't be progressively synced.

1 AppSet ≈ 1 Microservice

Assumed model. Not ideal when one ApplicationSet deploys different microservices that should roll independently.

Recap · Is It Stable?

Stable or Not Stable, That Is the Question

Kubernetes has navigated this before. Two options, two precedents.

Promote to Stable

  • Promoted to stable (GA)
  • API frozen: no new features
  • Bug fix only
  • Alternative built with new features
Strategy adopted for Ingress

Stay in Beta

  • Never promoted to stable
  • Deprecated while in beta
  • Longer grace period than what is mandatory
  • Alternative built in parallel
Strategy adopted for PodSecurityPolicy
Ingress: https://kubernetes.io/docs/concepts/services-networking/ingress/ PodSecurityPolicy: https://kubernetes.io/blog/2021/04/06/podsecuritypolicy-deprecation-past-present-and-future/
